# Tata Play Subscriber Retention & Support Copilot

> Educational capstone using deterministic synthetic data only. This is not real Tata Play data, policy, pricing or customer information.

## Overview

A four-part Python project: data foundation (A), leakage-aware churn prediction (B), subscriber segmentation and revenue-at-risk ranking (C), and support ticket/RAG/retention workflows (D).

## Reproduce

Use Python 3.11 or 3.12. The pinned versions in `requirements.txt` follow the assignment reference environment.

```bash
python -m venv .venv
# Windows: .venv\\Scripts\\activate
# macOS/Linux: source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements.txt
python generate_data.py
python part_a.py
python part_b.py
python part_c.py
python part_d.py
python copilot.py
```

The supplied `generate_data.py` and `mock_llm.py` are included unmodified. Part D downloads the open-source `all-MiniLM-L6-v2` embedding model once; no API key is needed. For optional live mode set `LLM_MODE=live` and `OPENROUTER_API_KEY` in the environment. Never commit credentials.

## Part A

`part_a.py` audits the raw CSVs, removes exact duplicates, normalises city and auto-renew values, marks impossible ages missing, repairs non-numeric recharge amounts from subscriber monthly recharge, and writes clean CSVs and `data/tataplay.db`. No missing values are imputed in Part A: imputation is learned from training rows only in Part B.

The four SQL analyses are in `sql/queries.sql`: revenue by plan, subscribers with no successful recharge, within-city ranking using three window functions, and a running recharge total.

Run `python part_a.py` to print the audit and query results. Compare them with the exact checkpoints in the supplied assignment brief.

## Part B

`features.py` builds the three six-month recharge features using the 2026-03-31 observation cutoff. `part_b.py` makes stratified train/validation/test splits, builds a numeric/categorical preprocessing pipeline, tunes logistic regression and random forest with five-fold stratified CV, chooses a threshold by the stated INR error costs on validation only, then evaluates on test. The two leakage columns `closure_request_logged` and `next_cycle_recharge_inr` are not used as model features.

Outputs: `outputs/churn_model.joblib`, `outputs/test_scores.csv`, and `outputs/threshold.txt`.

## Part C

`part_c.py` evaluates K-Means from K=2 through K=8, selects K=4 as a documented starting choice, profiles segments, assigns the hand-worked subscriber to its nearest centroid, fits Ridge and Lasso spend models, and ranks test subscribers by expected monthly revenue at risk.

Outputs: `outputs/segments.csv` and `outputs/retention_priority.csv`.

## Part D

`llm_client.py` uses the deterministic offline mock by default and retries HTTP 429 responses up to three times. `part_d.py` runs weak/zero-shot/few-shot ticket classification, Pydantic extraction with repair attempts, policy chunking and cosine retrieval evaluation. `copilot.py` re-scores each priority subscriber with the saved churn model, retrieves policy context and validates the generated retention brief.

Outputs: `outputs/ticket_classification.csv`, `outputs/ticket_extractions.jsonl`, `outputs/rag_eval.csv`, and `outputs/retention_briefs.jsonl`.

## Limitations and Next Steps

- The dataset is synthetic, small and generated from a fixed process; metrics do not establish real-world performance.
- There is only one observation window and one April 2026 churn label period, so temporal generalisation is untested.
- The offline mock LLM is deterministic and is not representative of a production language model.
- The retrieval rejection threshold is a narrow calibration boundary and should be validated on a larger labelled question set.
- The revenue-at-risk ranking uses the held-out test sample as the assignment's specified demonstration; a production workflow should score a current live subscriber population instead.
- Production deployment would require privacy controls, monitoring, drift checks, human review, model governance and policy versioning.
